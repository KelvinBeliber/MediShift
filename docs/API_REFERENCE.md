# MediShift — API Reference & Roadmap

This document explains what has actually been built so far: every API endpoint, organized by department/section, plus an honest roadmap of what's done and what isn't.

---

## How the system is put together

- **Node/Express API** — `http://localhost:5000/api/v1` — this is the main backend. Everything the frontend will eventually talk to goes through here.
- **Python scheduling service** — `http://localhost:8000` — a separate small service that runs Google OR-Tools (the AI scheduling engine). It is **internal only**: the frontend never talks to it directly, only the Node API does, when a manager clicks "Generate Schedule."
- **MongoDB** — the database, running locally.

**Auth model:** every endpoint except `/auth/register`, `/auth/login`, `/auth/refresh`, `/auth/forgot-password`, `/auth/reset-password`, and `/auth/verify-email` requires a Bearer token (`Authorization: Bearer <token>`) obtained from login. Most endpoints additionally require a specific **permission** — see the [Roles & Permissions legend](#roles--permissions-legend) at the bottom for who can do what by default.

### Known gaps and simplifications (so nothing surprises you later)

- **Excel/PDF export** isn't built for payroll — only CSV.
- **Holiday calendar**: `holiday`, `on_call`, `overtime`, and `half_day` shift types aren't auto-generated by the AI scheduler (there's no holiday calendar data model yet). A manager can still create them manually, and the AI generator will happily assign staff to them.
- **Employee shift preferences**: the AI solver supports rewarding an employee's preferred shift types, but there's no field on the Employee record yet to set that preference — it's currently always empty.
- **GPS/QR attendance**: the data model supports recording a clock-in method and GPS coordinates, but there's no actual GPS/QR capture logic (that's a frontend/mobile concern).
- **Document upload needs real Cloudinary credentials** to actually work — `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET` are blank by default, and the API returns a clear error (not a crash) until they're set.
- **Audit logging is scoped, not exhaustive** — it captures who/when/what for the sensitive mutations listed above (employee/department writes, leave approvals, schedule publish, payroll finalize), not every single write in the system. It also records `after` state but not a full `before`/`after` diff.
- Test coverage is strong on business logic (services, validators, the solver) but thin on `src/sockets/` (30%) and the raw HTTP-fetch path in `schedulingClient.ts` (27%) — both require a live socket/HTTP connection to test meaningfully rather than being mocked, which is lower priority than the business-logic coverage already in place.
- Only the two servers running locally have been tested — nothing has been deployed anywhere.

### Bugs found and fixed by the test suite

Writing these tests surfaced real bugs that manual testing had missed, all now fixed:
1. **Certification check silently broken** — `shiftAssignment.service.ts` populated `requiredCertifications` into full documents, then compared them with `.toString()`, which returns `"[object Object]"` for a populated doc instead of the hex ID. Every certification check was failing, rejecting even correctly-certified employees.
2. **Privacy leak in leave requests** — the `employee` role's default permissions included `leave:view` (meant for HR/managers to see *everyone's* requests), so every employee could see every other employee's leave requests. Removed from the base role; employees still see their own via a separate, unconditional code path.
3. **Same class of bug for shift swaps** — `shift_swap:view` had the same over-broad grant; removed for the same reason.
4. **HR couldn't manage attendance** — `hr_manager` had `attendance:view` but not `attendance:manage`, so HR couldn't correct records or run the mark-absentees job, despite owning payroll and leave approval. Added `attendance:manage` to HR's default permissions.
5. **Test-pollution bug in the test suite itself** — an early RBAC test mutated the shared `employee` role's permissions to prove permissions are resolved live from the database, but never restored them, silently corrupting that role for every test that ran afterward in the same process. Fixed by capturing and restoring the original permission set.
6. **A second test-suite bug, same family** — a reports test inserted two attendance records for the same employee on the same date, violating a unique index. It only started failing once more test files were added earlier in the run shifted MongoDB's background index-build timing — a reminder that a passing test isn't proof of a correct one. Fixed by using two employees instead of one.

## Roles & Permissions legend

Permissions are stored in the database, not hardcoded, but here's the **default** setup created by the seed script:

| Role | Can do |
|---|---|
| **super_admin** | Everything |
| **hospital_admin** | Everything except system settings |
| **hr_manager** | Employees, positions, certifications, leave approval, attendance viewing, payroll, announcements, reports |
| **department_head** | Their department's employees/schedule/attendance, leave approval, shift swap approval, announcements, messaging |
| **shift_coordinator** | Schedule creation/editing/AI-generation, attendance viewing, shift swap approval, messaging |
| **employee** | View their own schedule, clock in/out, request leave, request shift swaps, view announcements, messaging |

## API Reference by Section

### 1. Authentication — `/api/v1/auth`
*No token required except where noted.*

| Method | Endpoint | Description |
|---|---|---|
| POST | `/register` | Create a login account. Optionally links to an existing Employee record via `employeeId`. |
| POST | `/login` | Log in, returns access token + refresh token. |
| POST | `/refresh` | Exchange a refresh token for a new access token. |
| POST | `/logout` | 🔒 Revoke the current refresh token. |
| POST | `/forgot-password` | Request a password reset email. |
| POST | `/reset-password` | Complete a password reset using the emailed token. |
| POST | `/verify-email` | Verify an email address using the emailed token. |
| GET | `/me` | 🔒 Get the current logged-in user's profile, role, and permissions. |
| POST | `/change-password` | 🔒 Change your own password (requires current password). Revokes all other sessions. |

### 2. Roles & Permissions — `/api/v1/roles`
*🔒 Requires login only — read-only reference data for dropdowns etc.*

| Method | Endpoint | Description |
|---|---|---|
| GET | `/` | List all roles with their permissions. |
| GET | `/permissions` | List every permission that exists in the system. |

### 3. Employees — `/api/v1/employees`

| Method | Endpoint | Permission | Description |
|---|---|---|---|
| GET | `/me` | 🔒 logged in, no `employee:view` needed | Get your own linked employee profile. |
| PUT | `/me` | 🔒 logged in, no `employee:edit` needed | Update your own profile — **only** `phone`, `photo`, `address`, `emergencyContact`. Anything else (department, salary, status, etc.) is rejected. |
| GET | `/` | `employee:view` | List employees. Supports `?search=`, `?department=`, `?position=`, `?status=`, `?employmentType=`, pagination, sorting. |
| GET | `/:id` | `employee:view` | Get one employee's full profile. |
| POST | `/` | `employee:create` | Create an employee (auto-generates `EMP-000001` style ID if not given). |
| PUT | `/:id` | `employee:edit` | Update an employee. |
| DELETE | `/:id` | `employee:delete` | **Soft delete** — sets status to `terminated`, deactivates their login if they have one. |
| GET | `/:id/documents` | self or `employee:view` | List an employee's uploaded documents. |
| POST | `/:id/documents` | self or `employee:edit` | Upload a document (`multipart/form-data`: `file` + `type`). See [Documents](#documents-details) below. |

### 18. Documents — `/api/v1/documents` <a name="documents-details"></a>
*Upload/list live under `/employees/:id/documents` (see section 3) — this is just the delete endpoint, since it doesn't need the employee ID in the path.*

| Method | Endpoint | Permission | Description |
|---|---|---|---|
| DELETE | `/:id` | self (owner) or `employee:edit` | Delete a document — removes it from Cloudinary, the database, and the owning employee's document list. |

### 19. Settings — `/api/v1/settings`
*Everything here requires `system_settings:manage` — by design, only `super_admin` has this (not even `hospital_admin`).*

| Method | Endpoint | Description |
|---|---|---|
| GET | `/` | List all settings (excludes internal keys — see below). |
| GET | `/:key` | Get one setting by key. |
| PUT | `/:key` | Create or update a setting (`{ value, description }`). |
| DELETE | `/:key` | Remove a setting. |

Keys starting with `counter:` are internal (used for sequential IDs like `EMP-000001`) and are blocked from being read, written, or deleted through this API — they're filtered out of listings and any direct access returns 403.

### 20. Audit Logs — `/api/v1/audit-logs`
*Requires `audit_log:view` — `super_admin` and `hospital_admin` only by default.*

| Method | Endpoint | Description |
|---|---|---|
| GET | `/` | List audit entries. Filter by `?entityType=`, `?entityId=`, `?user=`, `?action=` (`CREATE`/`UPDATE`/`DELETE`/`APPROVE`/`REJECT`/`PUBLISH`/`FINALIZE`), `?dateFrom=`, `?dateTo=`. |
| GET | `/:id` | Get one audit entry. |

Each entry records who did what, when, from what IP/user-agent, and the resulting state (`after`). Currently wired into: Employee create/update/delete, Department create/update/delete, Leave department-approve/HR-approve/reject, Schedule publish, Payroll finalize, and Document upload/delete. It's a scoped, curated set of sensitive actions — not a blanket log of every write in the system. Writing an audit entry never blocks or fails the operation it's recording (errors are swallowed and logged server-side).
